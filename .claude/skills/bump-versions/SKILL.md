# Bump versions

Updates every dependency of the monorepo to the newest release the stability rule allows, checks
each platform still builds, and opens one `chore` pull request.

## The stability rule

- A **stable** version only moves to a newer **stable** one, even when a newer pre-release exists.
- A **pre-release** (`alpha`, `beta`, `rc`, `dev`, `eap`, a milestone `-M1`) moves to the newest
  release of any kind: a newer pre-release, or the stable one once it ships (Supabase
  `3.9.0-beta-1` → `3.9.0`). It stays a pre-release only when nothing stable is newer.
- A new **major** is allowed when it is stable, but read its release notes first and look for the
  breaking changes this repository would hit (an API the code calls, a trigger a workflow uses, a
  tool flag a script passes). If one needs code changes beyond the bump, make them; if it needs a
  product or architecture choice, ask Pierre and leave that one out meanwhile.
- If the user names a version or a library, do that one even when the rule would say otherwise.

## Where the versions live

| Platform | File | How to find the newest |
|---|---|---|
| Gradle libraries and plugins | `gradle/libs.versions.toml` | `check_gradle_versions.py` (below) |
| Settings plugins | `settings.gradle.kts` (`foojay-resolver-convention`) | `check_gradle_versions.py` |
| Gradle wrapper | `gradle/wrapper/gradle-wrapper.properties` | `check_gradle_versions.py` |
| Android SDK levels | `android-compileSdk`, `android-targetSdk`, `android-minSdk` in the catalog | Not bumped here, see below |
| Apple | `packages:` of `iosApp/project.yml` (Firebase) | `gh api repos/firebase/firebase-ios-sdk/releases/latest --jq .tag_name` |
| Web | `webApp/package.json` and `webApp/package-lock.json` | `npm view <package> dist-tags.latest` (the stable line); `npm --prefix webApp outdated` once `node_modules` is installed |
| Kotlin/JS npm lock | `kotlin-js-store/yarn.lock` | Generated by Gradle from the Kotlin libraries, never edited by hand |
| CI | `uses:` of `.github/workflows/*.yml` and `.github/actions/*/action.yml`; `java-version`, `node-version` | `gh api repos/<owner>/<repo>/releases/latest --jq .tag_name` |

Run the catalog check from the repository root (or pass the worktree path). It runs on the Python
3.9 that ships with macOS and needs no packages:

```bash
python3 .claude/skills/bump-versions/check_gradle_versions.py .
```

It prints one line per `[versions]` entry with the newest allowed release, `BUMP` in front of the
ones that moved, read from the `maven-metadata.xml` of Google's Maven, Maven Central and the Gradle
Plugin Portal. Entries no library or plugin points at (the SDK levels) are listed as skipped.

## The pins that move together or stay put

- **`kotlin`** is shared by the Kotlin plugins and the Compose compiler. **`ksp`** has its own line
  (KSP2, `2.3.x`) and is not tied to the Kotlin version any more; still build after bumping either.
  `docs/architecture/stack.md` names the Kotlin version: update it with the catalog.
- **`androidx-lifecycle`** is used by JetBrains' multiplatform `lifecycle-viewmodel` and by the
  AndroidX artifacts of the Android UI. Bump it only when **both** groups have the release
  (`org.jetbrains.androidx.lifecycle` usually ships after `androidx.lifecycle`).
- **`androidx-compose-material3`** overrides the Compose BOM because the Material 3 Expressive APIs
  only ship on the 1.5 pre-releases. Once the BOM pins a stable 1.5, drop the override and its
  comment and let the BOM decide.
- **`@js-joda/core`** in `webApp/package.json` is the exact version kotlinx-datetime's JS target
  depends on (find it in `kotlin-js-store/yarn.lock`). Keep the two equal: bump it only when
  kotlinx-datetime moves to a new one, never to npm's latest.
- **`blitzsplit-shared`** is a `file:` dependency on the JS library `:shared` builds: never bumped.
- **Firebase** on Apple (`iosApp/project.yml`) and on the web (`firebase` in npm) are separate SDKs
  with separate release lines; bump each to its own newest.
- **`Quartel-Enterprise/claude-review`** and **`Quartel-Enterprise/copied-code-check`** are bumped
  by Dependabot (`.github/dependabot.yml`), in pull requests of their own; every other action is
  bumped by hand, here. Leave those two out unless the user asks, and check `gh pr list --author
  app/dependabot` for an open one first so the two pull requests don't touch the same lines. Every
  `uses:` of claude-review must pin the same release (`claude-review-refs.yml` fails otherwise), and
  copied-code-check's `uses:` in `duplication.yml` is also what `scripts/cpd.sh` runs.
  **`quare-ktlint-rules`** in the catalog is read by `scripts/ktlint.sh`.
- **Android SDK levels**: a new `targetSdk` changes how Android runs the app, and a new `minSdk`
  drops users. Don't bump them here: report a newer API level to the user and leave it for its own
  task.
- **Gradle wrapper**: bump it with Gradle itself, so the scripts, the jar and the checksum change
  together: `./gradlew wrapper --gradle-version <version>` (run it twice: the second run uses the
  new wrapper to write its own files).
- **CI runtimes** (`java-version`, `node-version`) follow the project's toolchain, not npm or
  Maven; change them only when the build needs it.

## Step-by-step workflow

### 1. Start the task

Use the `start-task` skill with the `chore` type (`chore/bump-libraries`, or
`chore/bump-<library>` when the user named one). No device is needed.

### 2. Find the newest allowed versions

Run, in parallel:

- `python3 .claude/skills/bump-versions/check_gradle_versions.py .`
- the npm check of `webApp/package.json`, which works without `node_modules`:

  ```bash
  node -e 'const p = require("./webApp/package.json"); const { exec } = require("child_process");
    const deps = Object.entries({ ...p.dependencies, ...p.devDependencies }).filter(([, range]) => !range.startsWith("file:"));
    Promise.all(deps.map(([name, range]) => new Promise((done) =>
      exec(`npm view ${name} dist-tags.latest`, (_, out) => done(`${name.padEnd(28)} ${range.padEnd(16)} ${String(out).trim()}`))
    ))).then((lines) => console.log(lines.join("\n")))'
  ```

- `gh api .../releases/latest` for each Swift package of `iosApp/project.yml` and each `uses:` of
  the workflows (`git grep -h "uses: " -- .github | sort | uniq -c` lists them).

Apply the stability rule and the pins above to the list, then show the user a short table of what
moves (current → new, a ⚠ on the majors) before editing.

### 3. Read the release notes of the majors

For each major, read its release notes (`gh api repos/<owner>/<repo>/releases`, the library's
changelog) and check the breaking changes against this repository. For example, `actions/checkout`
v7 stopped checking out fork pull requests on `pull_request_target` and `workflow_run`: harmless
only because no workflow here checks out on those triggers.

### 4. Edit the versions

- The catalog: edit the `[versions]` lines; keep their comments true.
- The web: edit `webApp/package.json` keeping each entry's range style (`^`, `~`, exact), then
  `npm --prefix webApp install` to rewrite `package-lock.json` (it needs the JS library of
  `:shared` built first: `npm --prefix webApp run shared`).
- Apple: edit `from:` in `iosApp/project.yml`, then `./iosApp/generate-project.sh`.
- CI: replace every `uses: <action>@<old>` with the new tag, in all files at once.
- Any doc that names a version you bumped (`git grep -n "<old version>" -- docs README.md`).

### 5. Build every platform

A bump touches the build, so run the full set of checks, each through `scripts/heavy-check.sh`,
one after the other:

```bash
./scripts/heavy-check.sh ./gradlew build :koverVerifyCi assertModuleGraph --continue
./scripts/heavy-check.sh npm --prefix webApp run build
./iosApp/generate-project.sh
./scripts/heavy-check.sh xcodebuild -project iosApp/BoraRachar.xcodeproj -scheme BoraRachar-iOS \
  -destination 'generic/platform=iOS Simulator' ARCHS=arm64 \
  -derivedDataPath iosApp/build/DerivedData build -quiet
./scripts/heavy-check.sh xcodebuild -project iosApp/BoraRachar.xcodeproj -scheme BoraRachar-macOS \
  -destination 'platform=macOS' -derivedDataPath iosApp/build/DerivedData \
  CODE_SIGNING_ALLOWED=NO build -quiet
```

- If the JS build stops with "Lock file was changed", a Kotlin library brought new npm packages:
  run `./gradlew kotlinUpgradeYarnLock` and commit `kotlin-js-store/yarn.lock`.
- Look for new deprecation warnings (`grep "^w: .*deprecated"` in the Gradle log, compared with
  main) and move the code to the replacement the warning names, keeping the behavior: material3
  `1.5.0-rc01` deprecated the `Slider(value, …)` overload for the one that takes a `SliderState`.
- A JS browser suite that ends with "Test running process exited unexpectedly" lost its headless
  browser, usually to the load of other builds, not to the bump: rerun that module's
  `jsBrowserTest` alone before looking for a cause.
- After `npm install`, compare `npm --prefix webApp audit` with the one of `origin/main` before
  blaming the bump: an advisory already on main (a transitive package a library pins) is not this
  pull request's to fix, and `npm audit fix --force` would downgrade that library. Mention it in the
  description instead.
- If a library's new release breaks the build (a deprecation turned error, a renamed API), fix the
  code when the fix is mechanical. When it isn't, put that library back on its old version, tell
  the user why, and go on with the rest.

### 6. Open the pull request

Use the `create-pr` skill. Title it `chore: bump <the libraries>` (or `chore: bump the libraries of
every platform` when there are many), and list each bump as `name old → new` in the description,
with a line on what each major needed.
